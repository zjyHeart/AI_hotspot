# 信息源可靠性改进方案（用户已确认，已实施）

> 历史本机版记录：以下实际 AI 调用来自当时的兼容服务，不能作为公开版 OpenRouter 真实联调的证明。当前对接见 [OpenRouter 发布版说明](openrouter-publication.md)。

日期：2026-10-04 提案；2026-10-05 用户确认后实施。下文保留确认时的方案与初始依据，当前代码和验证结果见 [实施验收记录](reliability-validation-2026-10-05.md)。用户后续已配置SerpAPI Key，Google/Bing真实联调已通过，见[专项记录](serpapi-validation-2026-10-05.md)。

## 目标与当前依据

用户截图提出：X 混入低价值回复；情报来源过于集中，需要多个搜索引擎获取材料。

已检查当前代码：

- `src/server/sources.ts` 的 twitterQuery 不排除回复，tweetSchema 未显式消费 isReply / inReplyToId；只记录纯转发与互动数，未实施入库前质量筛选。
- 系统已有 X / HN / GitHub / RSS，不是只有 X。默认 RSS 仅两个源；HN 材料主要为标题、讨论文字和外链，未读取链接原文。GitHub 搜索的是近期更新仓库，不是正式发布公告。
- `src/server/scanner.ts` 对待分析记录直接 limit(batchSize)，未显式排序、按来源公平分配或按质量筛选。扩展采集源后也可能出现积压和来源偏置。
- `src/server/ai.ts` 的一手来源依赖少量硬编码账号/机构；以 originKey 判断独立性，尚未系统处理同一原文被跨渠道发现、转载与同机构多个域名。
- HTTP 获取已有重定向、大小限制与公开地址检查，可复用并加强连接到实际解析地址的校验。
- 本次 Web 端口没有运行；只读代码和数据库用于了解状态。API 能力根据 MCP 文档确认，运行效果必须在批准后的独立数据库联调中验证。

## 推荐的数据流程

多渠道发现 → 类型与质量过滤 → URL / 转载归一 → 按预算获取原文 → 来源公平调度 → 历史兼容 AI 服务 聚合与逐条引用 → 按具体说法判断证据 → 展示与通知。

搜索引擎是发现渠道，证据来自原始发布者。一篇文章同时通过 Google、Bing、HN 找到，应存为一份证据，保留全部发现路径。

## 1. X 质量过滤

- 保留 twitterapi.io；默认排除普通对话回复、纯转发，避免进入主情报候选队列。作者连续自回复线程仅在追溯已入选原帖时作为补充材料，不单独作为热点。
- 上游查询过滤与本地响应字段检查并用。使用 isReply、inReplyToId、retweeted_tweet 等字段。上游操作符先真实验证；若不可靠，以本地字段过滤为准。缺失字段记为未知，不能擅自当原创。
- 不使用“回复数为零”或“没有蓝标”作为排除条件：原创公告也可能暂无互动，蓝标不能证明真实性。
- 配置关注账号、屏蔽账号及渠道质量模式。关注账号 / 可追溯官方原文的原创发布不强制互动门槛；一般社区内容初始建议点赞 ≥20 或转发 ≥5，再结合实质信息、主题相关性与广告特征判断。阈值是待真实样本调优的提案，不是真实性证明。
- 低互动但指向可验证发布原文的新项目可以作为发现线索，获取原文后再判定；不能仅因陌生作者或低粉丝量过滤掉小众项目。
- 泛词 Agent 建议明确监控领域，例如 AI Agent / 人工智能代理，并提供可见的中英检索扩展与排除词，不静默修改用户关键词。
- 记录过滤原因与计数，不在默认原始候选列表展示被过滤噪声。过滤材料的元数据可在采集诊断中审计，不删除历史文件或业务记录。

## 2. 多搜索引擎与直接信息源

首版建议通过 SerpAPI 的同一 Key 接入 Google（engine=google）和 Bing（engine=bing）。两个适配器分别记录健康状态、请求预算和检索结果；同一供应商故障仍会影响两个引擎，RSS / GitHub / HN / X 继续独立工作。

- 用于发现官网公告、产品博客、版本发布及独立报道。仅消费 organic_results 的来源链接和摘要，不将搜索 AI 答案直接作为事实证据。
- 第一轮发现只执行每引擎一个主题查询、读取第一页；默认最多保留前 10 个候选，具体返回数以 API 当前能力为准，不依赖未经核实的 num 参数。
- 对待核实且值得关注的具体事件进行有上限的补充检索，使用主体、版本、动作与时间限定，避免同名或历史事件混入。
- 扩展经过逐一验证的官方 RSS / Atom 目录，支持启停；不假定任意机构存在 RSS，也不将无法读取的源显示为成功。
- HN 保留讨论页，同时获取公开外链原文；讨论帖仅提供讨论依据。
- GitHub 区分仓库更新、正式 Release 和 Changelog。关注仓库使用实际发布记录；普通 push / Star 总量不能解释为新版本发布或短期增长。
- 搜索源按检索引擎显示发现路径，按实际发布者显示证据出处。

## 3. 正文获取与去重

- 默认在本机通过公开 HTTP 获取 HTML，使用 Mozilla Readability + DOM 解析提取正文。只把纯文本用于分析和页面展示，不执行网页脚本。
- 首轮每频道最多新抓取 6 篇优先候选正文，其他进入有界待处理队列；并发建议 2，控制超时、响应大小和 DOM 元素规模。正文长度上限与失败状态显式记录。
- 复用并完善公开地址 / 重定向检查；仅访问公开页面，不访问登录页、内网或带凭证地址。动态渲染、付费墙、PDF 等无法解析时记录失败或仅摘要，不能伪装成已读正文。
- 规范化链接，谨慎去除跟踪参数；保留影响正文/版本的参数。接受 canonical 前检查目标与内容一致性。
- 以规范 URL、原文指向和正文相似性合并跨引擎命中。转载文章、同机构多域名、X/HN 转述相同文章按共同来源归组；身份不确定时保守计数，不自动认定独立报道。
- 保存 discoveredAt / fetchedAt / publishedAt（发布时间可能未知），不把抓取时间冒充发布时间。未知日期不得当作“刚发布”抬高热度；对旧文只允许匹配事件时补充上下文，不作为新发布通知触发依据。

## 4. 证据判断

改为可配置来源目录，包含实际发布者、官网域名、官方账号/仓库、验证依据与适用范围。用户可补充可信的小众项目；名称相同、AI 推断和付费认证不能自动建立官方身份。

- 有来源支持：读取的一手材料直接支持具体说法，并能确认发布者与项目/机构关系；例如“官方宣布发布”，不能进一步证明宣传的性能指标。
- 多源支持：至少两组独立发布者材料支持相同具体说法，检查版本、时间与主体一致，并排除明显转载/共同原文。
- 待核实：只有讨论、身份未知、正文获取失败或证据不足；在详情解释具体缺口。
- 存在争议：材料存在关键矛盾，保留双方来源。

保留本地逐字引用和文章 ID 校验；搜索摘要标记为摘要并限制其可支持的说法。AI 只读已采集内容，不自行编造来源、浏览结果或独立性证明。热度、相关性与证据状态分别计算；默认继续不推送待核实和争议内容。

## 5. 调度、积压与费用

- 按主题、来源维护独立进度；按来源轮转、质量和等待时长挑选 AI 批次，确保存在合格材料的非 X 来源有处理机会。
- 当其他来源有合格待处理内容时，建议限制 X 占本轮 AI 输入不超过约 40%；其他来源为空时允许重新分配，不虚构材料凑比例。额度不够时跨轮公平轮转，避免长期饿死某个来源。
- 先分辨低质候选，再消耗 历史兼容 AI 服务 分析额度；原文获取和事件核验均有独立限额。失败或缺 Key 不阻塞其他来源。
- 新过滤策略进入 checkpoint 指纹与队列处理版本，避免复用旧查询游标。历史积压执行新规则并保留审计结果；历史事件重新评估需独立操作，不重新发送旧提醒。
- 查询 / URL 抓取结果缓存，重复频道共享适用缓存，失败按退避策略重试。不得靠强制实时请求无限增加费用。
- 请求上限持久化，跨 worker 重启生效；同时提供每日与每月全局限额，达到预算时记录“预算暂停”。按保守的实际请求数控制本地预算，供应商账单另行核对。

### 推荐省费用配置（已确认）

- X、RSS、HN 和已有 GitHub 任务：保留默认 30 分钟。
- Google + Bing 常规网页发现：默认每 4 小时，可独立修改为 30 分钟等频率。
- 每频道每轮每引擎 1 次主题查询；全局事件补充核验最多 6 次搜索/天，每次按一个引擎请求计数。
- 全局搜索最多 30 次/天、900 次/自然月（最多31天），留出套餐余量；超过预算公平延后。
- 若有 2 个频道且全天运行：常规搜索 2 频道 × 2 引擎 × 6 轮/天 = 24 次/天，加最多 6 次补查，共最多 900 次/30 天（不计缓存减免）。

SerpAPI 官网在 2026-10-04 查询显示：Free 250 次/月；Starter $25/月、1000 次；Developer $75/月、5000 次；Production $150/月、15000 次。免费额度适合联调，不能按上述满负荷长期运行。价格和可用套餐以用户注册时控制台为准。

如要求两频道 Google+Bing 也每 30 分钟搜索，不计缓存与事件补查的上限为 5760 次/30 天；此配置超过当前 Developer 5000 次额度。不得在未确认频率/预算时直接打开全天高频调用。最终计费还包括已有 X 与 历史兼容 AI 服务，用真实调用数、tokens 分别统计。

## 分步交付

1. 先实现 X 类型过滤、质量诊断、查询领域配置、候选公平调度，修复现有源处理不足；通过独立数据库回归。
2. 接入 Google/Bing 搜索适配器、正文提取、缓存与预算；补足官方订阅目录和 GitHub 发布材料，在独立数据库真实验证。
3. 实现跨渠道去重、发布者归组与可配置来源身份；升级证据判断，保持引用校验和历史通知幂等。
4. 最小调整 Web：来源勾选/频率/预算、采集过滤统计、来源分布、原文/摘要标识和具体待核实原因。保留用户已验收的界面。
5. 提交验证报告给用户验收；本轮不开发 Agent Skill。

数据库仅增量迁移，先备份，旧字段/历史数据保留；新增字段区分帖子类型、正文状态、发现渠道、原文归组、过滤原因和策略版本。具体表结构在确认后按迁移与测试需要细化。

## 验收标准

- 已识别的普通回复与纯转发不会出现在默认主情报流；零互动的可信原创公告可保留。缺失类型字段时行为保守且可解释。
- 相同链接经两个搜索引擎发现只有一份证据；转载不能升级成多源支持；旧文及未知日期不伪装为新发布。
- 在 X 大量积压、其他来源同时有合格内容的测试场景中，非 X 来源获得处理机会。报告展示采集/过滤/入选/积压数量。
- 官方 RSS、Google、Bing、HN 外链和 GitHub 发布适配器分别真实验证，展示实际请求与原文；某源没有有效结果时据实说明，不承诺固定来源比例或伪造热点。
- 稳定 URL、正文引用、来源身份、证据升级、同名事件和版本差异有有意义的回归测试；抓取失败、SSRF/重定向、预算上限与通知幂等也验证。
- 达到预算不超量继续搜索；同一历史事件不因升级策略重复发邮件。业务测试使用独立临时数据库。
