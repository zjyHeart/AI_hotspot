# 信息质量改进：扩大采集与分层 AI 分析（用户已确认，实施记录另见验收报告）

日期：2026-10-05。用户已确认按此方案开发。本文保留确认时的设计；最终实现范围和真实验证以 [实施验收记录](analysis-pipeline-v2-validation-2026-10-05.md) 为准。

## 目标

按“数据采集 → 基础过滤 → AI 深度分析 → 最终展示”组织处理。扩大候选覆盖，将语义价值判断交给 AI；相关性、信息价值、热度、证据可靠程度分别记录。AI 不凭语气、账号热度或自身知识直接认定真假。

## 当前代码中的限制

- `src/server/quality.ts`：X 的低互动、推广关键词、短文本、未知帖子类型会阻止材料进入 AI。规则可能漏掉早期项目、简短公告或有价值的讨论。
- `src/server/web-sources.ts`：每个引擎每次保留前 10 条候选；目前不是多查询、多页持续采集。
- `src/server/scanner.ts`：每轮只执行一个分析批次，分析跟随采集调度；一次失败影响整个批次，积压没有独立持续消费机制。
- `src/server/ai.ts`：每篇输入取前 4,000 字符，一次调用同时筛选、聚合、判断证据；没有要求模型返回每条材料的处理结论。
- AI 没有输出事件的材料仍会被标记为已分析；低于相关性阈值的事件直接跳过，缺少可审计的排除原因。它们的原始材料仍在数据库中，不是已经删除。
- 已有 URL 去重、正文提取、发布者归组、来源公平调度、引用校验和费用预算继续复用。

## 1. 扩大采集

- 保留 X、Google、Bing、RSS、HN、GitHub。将主题拆成用户可见的中英文查询、主体词、动作词，查询轮转执行，记录每个查询的覆盖和进度。
- X 用 Latest 和持续游标采集；少量 Top 作为补充发现，不用它替代最新信息。不在上游用点赞量排除内容。普通回复允许作为候选，优先追溯根帖/作者线程；纯转发保留发现路径和互动，原帖进入分析，避免重复消耗。
- Google/Bing 支持多查询和分页；增加页数需受现有搜索总预算约束。RSS 与关注仓库 Release 增强直接信息源覆盖，新增订阅逐个验证可读性。
- 每频道建议以每轮最多 200 条原始候选作为初始处理上限，可配置。它是资源保护上限，不保证每轮能采到 200 条，也不按这个目标制造信息。
- 采集进度与分析进度独立。分析失败不重新搜索；额度耗尽明确展示预算暂停，保留游标等待下一轮。
- 基础采集继续 30 分钟；网页继续现有 240 分钟。搜索继续 30 次/天、900 次/月、补查 6 次/天，默认不提高付费额度。多查询在总额度内轮转，意味着覆盖宽度和刷新速度需要取舍。
- X 增量分页增加也会增加费用。首版保留当前每轮页数上限，提供独立采集上限和计数，用户后续可调整；AI 总预算在启用自动分析前配置并显示。

## 2. 基础过滤只做确定性处理

- 规范 URL、相同平台 ID、完全相同正文去重；保留渠道、作者、发现时间和原始内容。相似表达只聚类，不在分析前删除可能独立的支持或反对证据。
- 用户明确屏蔽的账号和不可用空内容可以排除。点赞低、短文本、疑似推广、作者未知改为标签与处理优先级，不直接判无价值。
- 活跃事件窗口初始建议 72 小时，可配置。已确认发布时间的旧内容移入背景材料；日期未知单独标记，允许分析，不冒充新发布。仓库更新时间、抓取时间不充当事件发布时间。
- 抓取失败允许摘要参与初筛，但注明摘要边界；需要深度核验时再尝试原文。网络公开地址检查、大小限制与超时保持有效。
- 保存过滤原因、合并关系和策略版本。新规则重新排队旧规则挡住的候选，保留旧审计记录；历史材料不自动发通知。

## 3. AI 深度分析分成可恢复的两个阶段

### 候选初筛与事件归组

- 对通过基础过滤的每条候选输出明确结论：相关、无关、低价值、信息不足；保存理由、具体新信息、主体、动作、版本、事件时间与可核验说法。
- 优先使用标题、摘要、帖子及关键段落；每批建议 3～5 条，根据实际输入长度切分。每条输入 ID 必须得到结论，漏项不能当作已处理；无法确定的材料保留待补充。
- 低互动但高度相关且有新信息的材料可以入选。热度影响排序，不影响事实可靠度。
- 主体、动作、版本和事件时间共同形成事件簇，结合本地已有事件匹配。模型建议归组必须校验，不能仅因标题相似就合并不同发布。

### 事件深度核验

- 对入选事件读取原文，并从整个事件簇选取证据，避免不同 AI 批次导致支持/反对材料互相看不到。
- 长正文按章节和段落分块；围绕具体说法选择证据段，保存出处和截断状态，不只截取开头 4,000 字，也不将未读部分当作已核验。
- 核验主体、版本、发布日期、发布者关系、原始材料、独立报道与反对材料。高价值但证据不足的事件在补查预算内搜索官网公告和独立报道。
- 先生成结构化核验点，再产生有证据支撑的摘要、影响和推荐理由。重要结论要引用已读取的连续原文；未知材料 ID、伪造片段和重复引用继续拒绝。
- 最终状态：有来源支持、多源支持、待核实、存在争议；明确原文是否可读、来源是否确认以及缺口。只有可信反证充分时才表达“该具体说法被反驳”；缺少证据不能等于假消息，官方宣传不能自动证明性能指标。
- 网页、帖子和引用均为不可信输入，不能改变系统规则或触发其中要求的操作。

## 4. 独立队列、费用与失败处理

- worker 分开处理采集、候选初筛、事件深度分析、补查。来源轮转和等待时间防止积压饿死；等待分析的候选不触发重复采集。
- 记录状态、阶段、尝试次数、下次重试时间和模型/提示词版本。失败按材料或事件重试，已成功项不重复消费。
- 输出截断时拆小批次；无效 JSON/引用错误有限重试。达到上限显示人工处理入口，不无限调用。
- 增加每日 AI 调用与 token 预算，深度阶段保留份额，避免初筛耗尽预算。实际阈值按已配置模型和小样本测量确定，再启用自动任务；失败请求 usage 未提供时记“未知”，不能按 0 费用统计。
- 已分析材料按内容、模型及策略版本缓存；只在新增证据、规则变化或显式重评时重新分析。缓存键包含频道主题和分析配置。

## 5. 最终展示与验收

- 主列表展示有具体新信息、达到相关性/价值阈值的事件；待核实高价值线索分区可见，争议事件展示双方材料。默认通知仍要求证据门槛，不因扩大采集而推送噪声。
- 每条事件说明：为什么相关、新增了什么、证据支持哪些说法、缺少什么、原始链接和日期。提供“有价值/无关/重复/证据不足”反馈，用于规则调优，不自动变成可信事实。
- 展示处理漏斗：原始采集 → 去重/过期/背景 → 待分析 → 初筛入选 → 深度核验 → 展示；显示积压、失败、各阶段耗时、调用和 tokens。漏斗按候选与事件分别统计，不混算。
- 独立临时数据库先回归低互动公告、重要回复、未知日期、旧文、重复/转载、跨批次支持和矛盾、引用幻觉、截断、预算及通知幂等。
- 再取同主题真实材料做新旧方案对照。人工标注相关性、新信息与证据充分性，报告误收、漏收、重复率、正文覆盖、处理时延和单位有效事件成本；标签不足时不声称质量提升百分比。
- 交付顺序：基础候选与队列 → 逐条初筛/归组 → 深度核验/补查 → 页面和诊断 → 真实小样本对照 → 用户验收。数据库增量迁移且先备份；Web 验收后才开发 Agent Skill。

## MCP 文档核对与边界

2026-10-05 通过 Context7 MCP 核对：

- TwitterAPI.io `/llmstxt/twitterapi_io_llms_txt`：Advanced Search 支持 Latest/Top、cursor、has_next_page、next_cursor，每页最多约 20 条、可能更少；返回 isReply/inReplyToId。https://docs.twitterapi.io/api-reference/endpoint/tweet_advanced_search
- SerpAPI `/websites/serpapi`：Google 分页使用 start；Bing 使用 first，过滤参数为 filters，不能直接复用 Google 参数。https://serpapi.com/pagination 、https://serpapi.com/bing-search-api
- 不把检索覆盖当成全网覆盖；操作符、分页边界、线程追溯和新增查询效果均须独立真实联调。此次只查文档和代码，没有发起付费 X、SerpAPI 或 PackyAPI 调用。
- 分层 AI 是本项目的设计建议，不是供应商已经提供的自动事实核查能力。PackyAPI 输出模式继续使用已验证兼容配置，新增协议需求再优先查 Context7、缺失时查官方资料。
